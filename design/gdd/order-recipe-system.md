# Order & Recipe System

> **Status**: In Design
> **Author**: Yan + agents
> **Last Updated**: 2026-09-28
> **Last Verified**: 2026-09-28
> **Implements Pillar**: Pillar 2 (Цена видна в чашке), Pillar 1 (Хаос за стойкой), Pillar 4 (Монеты за работу, очки за мастерство)

## Summary

Order & Recipe System задаёт пять напитков MVP как последовательности шагов
по станциям кухни и их цены (2/5/5/7/7 монет по трём уровням сложности).
Игрок видит её в каждом заказе: ряд жетонов показывает маршрут по кухне, а
цифра — сколько стоит чашка, и из этого складывается решение «один дорогой
или два дешёвых». Система статическая: она хранит рецепты, проверяет их при
загрузке и отвечает, совпадает ли чашка с рецептом и допустим ли следующий
шаг.

> **Quick reference** — Layer: `Core` · Priority: `MVP` · Key deps: `Kitchen & Station Layout`

## Overview

Order & Recipe System определяет, из каких шагов состоит каждый напиток на
кухне, и жёсткое правило: цена чашки равна числу шагов рецепта ± небольшой
разброс. Каждый шаг — это тип станции (чашка, лист чёрный/зелёный, кипяток
100°/вода 80°, лимон, подача), и система гарантирует, что рецепт никогда не
ссылается на станцию, которой физически нет на кухне (контракт
`station_types` из Kitchen & Station Layout). Игрок не взаимодействует с
этой системой напрямую — он читает её результат: заказ на тикете гостя и
цветные квадраты рецепта, которые превращаются в маршрут по кухне
(Pillar 1) и в понятную с одного взгляда цену (Pillar 2). Без этой системы
нет ни заказов, ни цены, ни различия между «дешёвым и быстрым» и «дорогим
и долгим» — то есть нет решения, которое делает партию интересной.

## Detailed Design

### Core Rules

1. Рецепт — упорядоченная последовательность шагов; каждый шаг, кроме
   последнего, соответствует ровно одному типу станции из `station_types`
   (Kitchen & Station Layout). Последний шаг — подача — не взаимодействие
   со станцией, а передача готовой чашки гостю с совпадающим заказом.
2. Каждый рецепт начинается с «чашка» (взять пустую чашку) и заканчивается
   «подача». Между ними — выбор листа (чёрный/зелёный) или готового
   холодного чая, вода нужной температуры (заварка идёт фоновым таймером —
   таймер и владение чайником принадлежат Brewing & Crafting Mechanic, не
   этой системе) и опционально лимон.
3. Температура воды обязана совпадать с цветом листа: чёрный лист
   заваривается кипятком 100°, зелёный — водой 80°. Несовпадение делает
   чашку негодной ни для одного заказа (чашка в мусорку) — само правило
   ошибки принадлежит Brewing & Crafting, эта система лишь определяет,
   какая пара «лист+температура» верна для каждого рецепта.
4. MVP отгружает ровно 5 рецептов в 3 уровнях сложности: Простой
   (1 — холодный чай), Средний (2 — чёрный/зелёный), Сложный
   (2 — средний + лимон). Полный набор (6–8 напитков) — область Alpha
   (Technical Considerations → Content Volume в game-concept). Точные
   последовательности (ID шагов — рабочие, до фиксации в ADR; `serve` —
   подача, не станция):

   | `recipe_id` | Уровень | Шаги |
   |---|---|---|
   | `cold_tea` | Простой | `cup` → `iced_tea` → `serve` |
   | `black_tea` | Средний | `cup` → `leaf_black` → `water_100` → `serve` |
   | `green_tea` | Средний | `cup` → `leaf_green` → `water_80` → `serve` |
   | `black_tea_lemon` | Сложный | `cup` → `leaf_black` → `water_100` → `lemon` → `serve` |
   | `green_tea_lemon` | Сложный | `cup` → `leaf_green` → `water_80` → `lemon` → `serve` |

   Лимон идёт после шага воды; может ли он быть добавлен до окончания
   таймера заварки, решает Brewing & Crafting Mechanic.
5. Каждый рецепт обязан начинаться с `cup` и заканчиваться единственным
   `serve`; рецепт, нарушающий это, — ошибка загрузки данных.
6. Цена фиксируется по рецепту (таблица данных), не вычисляется на лету из
   числа шагов — см. Formulas.
7. Шаги рецепта 1:1 совпадают с уже зафиксированными в систем-индексе
   цветовыми индикаторами (владеет отрисовкой HUD & Feedback UI): чашка —
   белый, холодный чай — фиолетовый, зелёный лист — зелёный, чёрный лист —
   оранжево-коричневый, кипяток — красный, вода 80° — синий, лимон —
   жёлтый.

### States and Transitions

Order & Recipe System — статическая, бесстейтовая система, как и Kitchen &
Station Layout: она описывает фиксированные определения рецептов, а не
runtime-состояние. Единственное состояние, которое ссылается на рецепт —
«какой рецепт заказал этот гость» — этой системе не принадлежит: им владеет
Guest AI & Patience.

### Interactions with Other Systems

| Система | Направление | Интерфейс |
|---|---|---|
| Kitchen & Station Layout | Upstream (hard) | `station_types` — шаги рецепта не могут ссылаться на несуществующий тип станции |
| Brewing & Crafting Mechanic | Downstream (hard) | Определения рецептов (шаги, температурная пара лист+вода) — Brewing владеет таймером заварки, слотом и правилом «ошибка → мусорка» |
| Guest AI & Patience | Downstream (hard) | Запрашивает рецепт (с ценой) для заказа спавнящегося гостя |
| Currency: Coins & Score | Downstream (hard) | Читает `recipe_price` для начисления монет; цена — один из множителей формулы очков (цена × 10 × (1 + доля терпения)) |
| Difficulty Curve & Session Pacing | Downstream (hard) | Читает уровень сложности рецепта (простой/средний/сложный), чтобы модулировать долю сложных заказов (0%→40%) в потоке |
| HUD & Feedback UI | Downstream (hard) | Читает список шагов рецепта и их цвета для тикета заказа и индикаторов прогресса |

## Formulas

Цена чашки во время игры берётся из таблицы данных. Формула времени
выполнения — инструмент балансировки: ею таблица проверяется, в рантайме
она не считается (Core Rule 6).

### Formula 1 — `recipe_price` (поиск по таблице)

The `recipe_price` formula is defined as:

`recipe_price = price_table[recipe_id]`

**Variables:**

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `recipe_id` | StringName | {`cold_tea`, `black_tea`, `green_tea`, `black_tea_lemon`, `green_tea_lemon`} | data file (определения рецептов) | Рецепт, который заказал гость (заказом владеет Guest AI & Patience) |
| `price_table` | Dictionary | 5 записей в MVP | data file | Таблица цен; рецепты одного уровня стоят одинаково |
| `recipe_price` | int | 2–7 в MVP | calculated | Цена в монетах; её читают Currency: Coins & Score (монеты и множитель очков) и HUD (тикет заказа) |

**Текущая таблица (временная):**

| `recipe_id` | Уровень | `n_steps` | `has_brew` | `recipe_price` |
|---|---|---|---|---|
| `cold_tea` | Простой | 3 | 0 | 2 |
| `black_tea` | Средний | 4 | 1 | 5 |
| `green_tea` | Средний | 4 | 1 | 5 |
| `black_tea_lemon` | Сложный | 5 | 1 | 7 |
| `green_tea_lemon` | Сложный | 5 | 1 | 7 |

`n_steps` считается вместе с чашкой и подачей. Прототип `kitchen-core`
использовал 2/5/9; сложный снижен до 7, потому что 9 нарушает оба
инварианта ниже (решение 2026-09-28, по рекомендации systems-designer и
economy-designer).

**Output Range:** целое от 2 до 7 в MVP. Формула ничего не ограничивает —
границы задаёт таблица; корректность таблицы проверяется инвариантами при
загрузке.
**Example:** гость заказал `green_tea_lemon` → `recipe_price = 7`. При
подаче с остатком терпения 0.4 очки по формуле Currency: `7 × 10 × (1 + 0.4)
= 98`. Гость с `cold_tea` при полном терпении: `2 × 10 × 2 = 40`.

### Formula 2 — `time_to_complete` и `coins_per_sec` (только для балансировки)

The `time_to_complete` formula is defined as:

`time_to_complete(recipe, η) = n_steps(recipe) × t_step + η × has_brew(recipe) × t_brew`

`coins_per_sec(recipe, η) = recipe_price(recipe) / time_to_complete(recipe, η)`

`η` — доля фоновой заварки, которую игрок тратит впустую: 0 — ушёл к
другим гостям, пока чай заваривается; 1 — всё время стоит у чайника.

**Variables:**

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `n_steps` | int | 3–5 | data file | Число шагов рецепта вместе с чашкой и подачей |
| `has_brew` | int | {0, 1} | data file | 1, если в рецепте есть заварка (средний и сложный уровни) |
| `t_step` | float, с | 2.0 | constant (`player-control-barista-movement.md`, Formula 4; реестр) | Среднее время шага «дойти + тапнуть» при скорости MVP. До 2026-09-28 — условные 3 с |
| `t_brew` | float, с | 3.0 (MVP) | constant (`brewing-crafting-mechanic.md`, Formula 1 — `t_brew_base`; реестр) | Длительность таймера заварки при `speed_multiplier` = 1.0. Авторитетно с 2026-09-28, значение прототипа подтверждено без изменений |
| `η` | float | 0.0–1.0 | calculated (аналитический параметр, в игре не реализуется) | Доля заварки, потраченная впустую |
| `time_to_complete` | float, с | 6–13 при текущих значениях | calculated | Оценка времени на рецепт |
| `coins_per_sec` | float | 0.33–0.70 при текущих значениях | calculated | Эффективность рецепта; по ней проверяется доминирование |

**Output Range:** `time_to_complete` растёт от η = 0 к η = 1 и не бывает
меньше `n_steps × t_step`. `coins_per_sec` в MVP лежит в 0.33–0.70.
**Example** (`t_step` = 2.0, `t_brew` = 3):

| η | Простой (2) | Средний (5) | Сложный (7) |
|---|---|---|---|
| 0 | 6 с → 0.333 | 8 с → 0.625 | 10 с → **0.700** |
| 0.5 | 6 с → 0.333 | 9.5 с → 0.526 | 11.5 с → **0.609** |
| 1 | 6 с → 0.333 | 11 с → 0.455 | 13 с → **0.538** |

*Пересчитано 2026-09-28 после фиксации `t_step` = 2.0 в Player Control (было 3 с: 0.22–0.47). Вывод не изменился, разрыв между уровнями вырос.*

**Вывод при текущих таймингах:** при заварке 3 с сложный заказ выгоднее по
монетам в секунду при любом η, а простой всегда слабее всех. Выбор «один
дорогой или два дешёвых» на одной арифметике времени не держится. Его
создают риск ухода других гостей, пока бариста занят длинным заказом
(Guest AI & Patience), бонус очков за остаток терпения (Currency) и риск
ошибки лист/вода. Чистая модель времени при `t_brew` = 3 дала бы почти
линейные цены (~2/3/3 при `t_step` = 2.0) — именно ту кривую, которую плейтест отверг, —
поэтому надбавка на средний и сложный уровни держится на находке плейтеста,
а не на этой формуле. Проверить — `/balance-check` (см. Open Questions).

### Проверочные инварианты

Проверяются при загрузке `price_table` и при каждой правке цен (предложены
economy-designer):

```
price_complex ≤ (price_simple + price_medium) × 1.15
price_complex ≤ price_medium × 1.6
```

В коде проверяются в целых числах, чтобы граница не зависела от
округления float: `price_complex × 100 ≤ (price_simple + price_medium) ×
115` и `price_complex × 10 ≤ price_medium × 16`. Равенство допустимо.

| Инвариант | 2 / 5 / 7 | 2 / 5 / 9 (прототип) |
|---|---|---|
| сложный ≤ (простой + средний) × 1.15 | 7 ≤ 8.05 — выполняется | 9 ≤ 8.05 — **нарушен** |
| сложный ≤ средний × 1.6 | 7 ≤ 8.0 — выполняется | 9 ≤ 8.0 — **нарушен** |

Если рецепты одного уровня стоят по-разному, инварианты проверяются по
самому дорогому рецепту сложного уровня и самым дешёвым рецептам простого
и среднего.

> Все значения временные. Итоговый баланс — через `/balance-check` вместе с
> вместимостью кассы (250 монет): при 2/5/7 средняя цена гостя к концу
> партии падает с 6.0 до ~5.2, доход за партию — примерно на 10–15%.

## Edge Cases

**Сопоставление чашки и рецепта**

Правило, которым владеет эта система: чашка совпадает с рецептом тогда и
только тогда, когда её список шагов (без подачи) в точности равен списку
шагов рецепта. Что лежит в чашке сейчас, отслеживает Brewing & Crafting
Mechanic.

- **Если чашка — полный рецепт одного уровня и префикс рецепта другого**
  (например, готовый `black_tea` и `black_tea_lemon`): она совпадает с
  `black_tea` и может быть подана такому гостю; добавление лимона
  превращает её в `black_tea_lemon`. Префикс — законное промежуточное
  состояние, не ошибка.
- **Если чашка не полная** (например, «чашка + чёрный лист» без воды): она не
  совпадает ни с одним рецептом, подача невозможна.
- **Если в чашке лист не той температуры воды** (чёрный + 80° или
  зелёный + 100°): для этой системы такой шаг недопустим (`is_valid_next`
  = false) — ни один рецепт так не продолжается. Brewing & Crafting вправе
  всё равно принять его, как в прототипе: чашка перестаёт быть префиксом
  любого рецепта, не совпадёт ни с одним заказом и уходит в мусорку.
  Решение «отказать или испортить чашку» — за Brewing & Crafting.
- **Если шаг идёт не в порядке грамматики рецепта** (лимон до заварки, вода
  без листа, второй лист): такой шаг не является допустимым следующим — ни
  один рецепт не начинается с получившейся последовательности. Эта система
  отвечает на вопрос «допустим ли шаг X после последовательности S»; отказ
  станции (мигает красным) реализует Brewing & Crafting / Player Control.
- **Если одинаковый рецепт заказали несколько гостей**: чашка совпадает с
  каждым из них. Кому именно она уходит, решает Guest AI & Patience.

**Целостность данных (проверка при загрузке)**

- **Если шаг рецепта ссылается на тип станции, которого нет в
  `station_types`**: загрузка данных рецептов падает с ошибкой, называющей
  рецепт и шаг. Некорректные данные в сборку не попадают.
- **Если у рецепта нет записи в `price_table`** или цена < 1: та же ошибка
  загрузки.
- **Если два рецепта имеют одинаковую последовательность шагов**: ошибка
  загрузки — одна чашка совпадала бы с двумя рецептами разной цены.
- **Если `price_table` нарушает инварианты из Formulas**: ошибка загрузки в
  debug-сборке и в тестах. Инварианты — ограничение на данные, а не на
  рантайм.
- **Если в каком-то уровне сложности нет ни одного рецепта**: ошибка
  загрузки. Difficulty Curve запрашивает рецепт по уровню и не должна
  получать пустой набор.

**Взаимодействие с экономикой и прокачкой**

- **Если касса полна**: `recipe_price` по-прежнему определена и
  используется в формуле очков; монеты не начисляются — это решение Till &
  Day Cycle, не этой системы.
- **Если бариста ускорен прокачкой (Alpha: ×1.15–1.5 на ходьбу и заварку)**:
  цены не пересчитываются — таблица фиксирована. Ускорение меняет
  `time_to_complete` и значит проверяется тем же `/balance-check`.

## Dependencies

**Upstream (эта система зависит от):**

| Система | Тип | Интерфейс |
|---|---|---|
| Kitchen & Station Layout | Hard | `station_types` — список типов станций на кухне; каждый шаг рецепта (кроме подачи) обязан ссылаться на тип из этого списка |

**Downstream (зависят от этой системы)** — все hard:

| Система | Что получает |
|---|---|
| Brewing & Crafting Mechanic | Грамматика шагов: допустим ли шаг X после последовательности S; совпадает ли последовательность чашки с рецептом (`matches(steps) → recipe_id \| none`) |
| Guest AI & Patience | Рецепт для заказа гостя (`recipe_id`) и правило совпадения чашки с заказом |
| Difficulty Curve & Session Pacing | Уровень сложности каждого рецепта и набор рецептов по уровню (`recipes_by_tier(tier)`) |
| Currency: Coins & Score | `recipe_price(recipe_id)` — монеты и множитель в формуле очков |
| HUD & Feedback UI | Список шагов рецепта и `recipe_price` для тикета заказа; соответствие шаг → цвет |

Имена функций — описание контракта, не API; реализация — в ADR.

**Двунаправленность:** Kitchen & Station Layout уже перечисляет Order &
Recipe System в своих Downstream с интерфейсом `station_types`. Ни одна
downstream-система ещё не спроектирована; каждая должна перечислить Order &
Recipe System в своей секции Dependencies.

## Visual/Audio Requirements

*Составлено с art-director. Рекомендации предварительные: hex-значения,
стиль глифов и шрифт цены утверждает `/art-bible`, раскладку тикета —
`/ux-design`.*

**Язык шагов: форма главная, цвет вспомогательный.** Каждый шаг — круглый
жетон своего цвета с тёмным глифом внутри (один тон «чернил» для всех).
Шаг обязан читаться в оттенках серого и при симуляции протанопии,
дейтеранопии и тританопии — «Цена видна в чашке» не должна зависеть от
зрения игрока.

| Шаг | Цвет | Глиф | От чего отличать без цвета |
|---|---|---|---|
| `cup` | белый | чашка с ручкой, сбоку | лимон — силуэт; чашке нужен контур |
| `iced_tea` | фиолетовый | высокий стакан с кубиком льда | вода 80° — стакан против капли |
| `leaf_green` | зелёный | раскрытый плоский лист с прожилкой | чёрный лист — силуэт и светлота |
| `leaf_black` | оранжево-коричневый | скрученный лист | зелёный лист — обязан быть заметно темнее |
| `water_100` | красный | капля с тремя струйками пара | вода 80° — число струек (3 против 1) |
| `water_80` | синий | гладкая капля с одной струйкой пара | кипяток |
| `lemon` | жёлтый | долька в разрезе | чашка — силуэт |

- Самая рискованная пара — зелёный и чёрный лист (одна категория, близкие
  тона при дейтеранопии): различаются силуэтом и светлотой; проверка в
  оттенках серого обязательна.
- Цифры «100»/«80» на жетоне не используются — при 20 dp не читаются.
- Верные пары складываются в семьи: чёрный + кипяток — тёплые, зелёный +
  вода 80° — холодные. Это подсказывает Core Rule 3 без текста.
- Глиф читается при 16 dp; целевой жетон на тикете — 20–24 dp.

**Состояния чашки не кодируются оттенком.** «Успех = зелёный, ошибка =
красный» запрещены: эти цвета уже значат лист и кипяток. Состояния
различаются светлотой, насыщенностью, значком и движением:

| Состояние | Чашка в мире | Жетоны | Тикет |
|---|---|---|---|
| Собирается | жидкость окрашена по содержимому, долька лимона на ободке | сделанные шаги полноцветные | — |
| Совпадает с заказом | нейтральный тёплый блик и пар | галочка поверх ряда | подходящий тикет один раз вспыхивает тем же акцентом, без постоянного пульса |
| Испорчена (неверная вода) | мутная серо-бурая жидкость без пара | ряд обесцвечен, крестик | — |

Требование к спрайту чашки (ассетом владеет Brewing & Crafting): содержимое
— цвет жидкости и лимон — видно по самой чашке в мире, не только по HUD.

**Аудио этой системе не принадлежит**: у неё нет runtime-событий. Звуки
шагов и ошибки — события Brewing & Crafting; тикет, подача, монеты —
HUD и Currency; ассеты и микс — Audio & Juice Feedback. Сквозное
требование: звук не может быть единственным носителем информации о
рецепте или состоянии чашки — Mini App на телефоне часто играют без звука.

## Game Feel

Система статическая, поэтому её «ощущение» — это скорость чтения, а не
отклик на ввод:

- **Заказ читается за один взгляд (< 1 с)** в толпе из 3–4 тикетов: длина
  ряда жетонов = сложность, крупная цифра = цена. Игрок не должен читать
  жетоны по одному, чтобы понять, «дорогой» заказ или нет.
- **Маршрут виден в рецепте.** Порядок жетонов совпадает с порядком обхода
  станций; игрок после 2–3 партий планирует путь по тикету, не глядя на
  кухню (Pillar 1).
- **Ошибка — моя.** Неверная вода даёт мгновенно заметную испорченную
  чашку; игрок сразу понимает, какой шаг он перепутал (конфликтующая пара
  перечёркнута), и не воспринимает это как «игра сломалась».
- **Решение «дорогой или дешёвые» ощущается как решение**, а не как
  арифметика: разница цен 2/5/7 достаточно крупная, чтобы её замечать, и
  недостаточно крупная, чтобы один уровень всегда доминировал (проверка —
  `/balance-check`, см. Open Questions).

Отклик на тапы, анимации шагов и тайминги — Player Control и Brewing &
Crafting.

## UI Requirements

Отрисовкой владеет HUD & Feedback UI; эта система задаёт, что тикет обязан
показывать:

- Цену заказа (`recipe_price`) — самый контрастный элемент тикета: крупная
  цифра со значком монеты, не меньше 16 dp.
- Шаги рецепта жетонами в порядке выполнения. Рекомендация art-director:
  не показывать `cup` и `serve` на тикете (они есть в каждом рецепте),
  тогда число жетонов 1/2/3 само показывает уровень сложности. Решение —
  за `/ux-design`.
- Уровень сложности не кодируется цветом тикета (все заметные оттенки
  заняты шагами). Запасной вариант, если число жетонов не читается на
  плейтесте: материал тикета по уровню (бумага / медная окантовка / золотая
  печать) — меняется светлота и фактура, не оттенок.
- Чашка в руках и чашка в слоте показывают тот же ряд жетонов, что и
  тикет, чтобы игрок сравнивал их напрямую.

## Acceptance Criteria

> Составлено с qa-lead. Фикстуры: фабрика `RecipeFixtures` (валидный набор
> MVP + мутаторы) и константный `station_types` из фикстуры; без случайности

### Данные MVP (Core Rules 1–5, 7)

1. **[Logic]** **GIVEN** отгружаемые данные рецептов и `station_types` из фикстуры, **WHEN** выполняется загрузка, **THEN** она завершается без ошибок и содержит ровно 5 рецептов с ID `cold_tea`, `black_tea`, `green_tea`, `black_tea_lemon`, `green_tea_lemon`.
2. **[Logic]** **GIVEN** загруженные данные MVP, **WHEN** перебираются все рецепты, **THEN** у каждого первый шаг `cup`, последний `serve`, и `serve` встречается ровно один раз.
3. **[Logic]** **GIVEN** загруженные данные MVP, **WHEN** каждый шаг, кроме последнего, сверяется с `station_types`, **THEN** все шаги найдены в `station_types`, а `serve` в нём отсутствует.
4. **[Logic]** **GIVEN** загруженные данные MVP, **WHEN** считается длина каждого рецепта, **THEN** `cold_tea` = 3, `black_tea` = `green_tea` = 4, `black_tea_lemon` = `green_tea_lemon` = 5.
5. **[Logic]** **GIVEN** загруженные данные MVP, **WHEN** проверяется пара лист+вода, **THEN** во всех рецептах с `leaf_black` за ним следует `water_100`, с `leaf_green` — `water_80`, а в `cold_tea` нет ни листа, ни воды.
6. **[Logic]** **GIVEN** загруженные данные MVP, **WHEN** запрашивается уровень каждого рецепта, **THEN** `cold_tea` = простой, `black_tea` и `green_tea` = средний, `black_tea_lemon` и `green_tea_lemon` = сложный (распределение 1/2/2).
7. **[Logic]** **GIVEN** загруженные данные MVP, **WHEN** запрашивается соответствие шаг → цвет, **THEN** `cup`→белый, `iced_tea`→фиолетовый, `leaf_green`→зелёный, `leaf_black`→оранжево-коричневый, `water_100`→красный, `water_80`→синий, `lemon`→жёлтый, и у каждого не-`serve` шага цвет есть.

### Formula 1: `recipe_price` (Core Rule 6)

8. **[Logic]** **GIVEN** загруженные данные MVP, **WHEN** вызывается `recipe_price(id)` для каждого из 5 ID, **THEN** результаты 2, 5, 5, 7, 7 соответственно, каждый типа int.
9. **[Logic]** **GIVEN** фикстура, где 4-шаговому рецепту назначена цена 11, **WHEN** вызывается `recipe_price` для него, **THEN** возвращается 11: цена берётся из таблицы, а не из числа шагов.
10. **[Logic]** **GIVEN** загруженные данные MVP, **WHEN** вызывается `recipe_price` для всех рецептов, **THEN** все значения в диапазоне [2, 7], а рецепты одного уровня стоят одинаково.

### Инварианты цен

11. **[Logic]** **GIVEN** отгружаемая `price_table` (2/5/7), **WHEN** проверяются инварианты, **THEN** оба выполняются, и загрузка успешна.
12. **[Logic]** **GIVEN** фикстура с ценами 2/5/9 (прототип), **WHEN** выполняется загрузка в debug/тестовом режиме, **THEN** возвращается ошибка, сообщение называет оба нарушенных инварианта.
13. **[Logic]** **GIVEN** фикстура с ценами 1/5/7, **WHEN** выполняется загрузка, **THEN** ошибка называет только инвариант `сложный ≤ (простой + средний) × 1.15` (700 > 690).
14. **[Logic]** **GIVEN** фикстура с ценами 4/4/7, **WHEN** выполняется загрузка, **THEN** ошибка называет только инвариант `сложный ≤ средний × 1.6` (70 > 64).
15. **[Logic]** **GIVEN** фикстура с ценами 2/5/8 (граница: 80 ≤ 80), **WHEN** выполняется загрузка, **THEN** она успешна: равенство не считается нарушением.
16. **[Logic]** **GIVEN** фикстура с разными ценами внутри уровней: простой {2, 3}, средний {5, 6}, сложный {7, 9}, **WHEN** выполняется загрузка, **THEN** возвращается ошибка: проверка берёт max сложного (9) и min простого и среднего (2, 5).
17. **[Logic]** **GIVEN** та же фикстура, но сложный {7, 8}, **WHEN** выполняется загрузка, **THEN** она успешна.

### Целостность данных при загрузке

18. **[Logic]** **GIVEN** фикстура, где шаг рецепта `black_tea` заменён на `honey`, которого нет в `station_types`, **WHEN** выполняется загрузка, **THEN** возвращается ошибка, сообщение содержит `black_tea` и `honey`, и ни один рецепт не становится доступен.
19. **[Logic]** **GIVEN** фикстура без записи `green_tea` в `price_table`, **WHEN** выполняется загрузка, **THEN** возвращается ошибка, сообщение содержит `green_tea`.
20. **[Logic]** **GIVEN** фикстуры с ценой `cold_tea` = 0 и = −1, **WHEN** выполняется загрузка каждой, **THEN** обе возвращают ошибку с `cold_tea`; фикстура с ценой 1 эту проверку проходит.
21. **[Logic]** **GIVEN** фикстуры, где у рецепта (a) первый шаг не `cup`, (b) последний шаг не `serve`, (c) пустой список шагов, **WHEN** выполняется загрузка каждой, **THEN** каждая возвращает ошибку с ID рецепта.
22. **[Logic]** **GIVEN** фикстура, где рецепт `black_tea_2` имеет ту же последовательность, что и `black_tea`, **WHEN** выполняется загрузка, **THEN** возвращается ошибка, сообщение содержит оба ID.
23. **[Logic]** **GIVEN** фикстура MVP (где `black_tea` — префикс `black_tea_lemon`), **WHEN** выполняется загрузка, **THEN** она успешна: префикс не считается дубликатом.
24. **[Logic]** **GIVEN** фикстура, где удалён единственный простой рецепт, **WHEN** выполняется загрузка, **THEN** возвращается ошибка, сообщение называет пустой уровень «простой».

### `recipes_by_tier`

25. **[Logic]** **GIVEN** загруженные данные MVP, **WHEN** вызывается `recipes_by_tier` для каждого уровня, **THEN** простой = {`cold_tea`}, средний = {`black_tea`, `green_tea`}, сложный = {`black_tea_lemon`, `green_tea_lemon`} (сравнение как множеств), и объединение трёх наборов равно всем 5 рецептам без пересечений.

### Совпадение `matches(steps)`

26. **[Logic]** **GIVEN** загруженные данные MVP, **WHEN** для каждого рецепта в `matches` передаются его шаги без `serve`, **THEN** возвращается ID этого рецепта (5 случаев).
27. **[Logic]** **GIVEN** последовательность [`cup`, `leaf_black`, `water_100`], **WHEN** вызывается `matches`, **THEN** возвращается `black_tea` (полный рецепт и одновременно префикс `black_tea_lemon`).
28. **[Logic]** **GIVEN** неполные последовательности [], [`cup`], [`cup`, `leaf_black`], [`cup`, `leaf_green`], **WHEN** вызывается `matches` для каждой, **THEN** каждый раз возвращается none.
29. **[Logic]** **GIVEN** последовательности [`cup`, `leaf_black`, `water_80`], [`cup`, `leaf_green`, `water_100`] и они же с добавленным `lemon`, **WHEN** вызывается `matches`, **THEN** все 4 возвращают none.
30. **[Logic]** **GIVEN** последовательности [`cup`, `leaf_black`, `lemon`, `water_100`] и [`cup`, `iced_tea`, `lemon`], **WHEN** вызывается `matches`, **THEN** обе возвращают none.
31. **[Logic]** **GIVEN** загруженные данные MVP и копия списка рецептов до вызова, **WHEN** `matches` дважды вызывается с одним и тем же входом, **THEN** оба результата равны, а данные рецептов не изменились.

### Грамматика `is_valid_next(S, x)`

32. **[Logic]** **GIVEN** S = [], **WHEN** проверяются все 7 не-`serve` шагов, **THEN** true только для `cup`.
33. **[Logic]** **GIVEN** S = [`cup`], **WHEN** проверяются все шаги, **THEN** true только для `iced_tea`, `leaf_black`, `leaf_green`; `water_100`, `water_80` и `lemon` дают false.
34. **[Logic]** **GIVEN** S = [`cup`, `leaf_black`], **WHEN** проверяются шаги, **THEN** `water_100` = true; `water_80`, `leaf_green`, `leaf_black`, `lemon` = false. Симметрично для S = [`cup`, `leaf_green`]: true только `water_80`.
35. **[Logic]** **GIVEN** S = [`cup`, `leaf_black`, `water_100`], **WHEN** проверяются шаги, **THEN** true только для `lemon`. **AND GIVEN** S = [`cup`, `iced_tea`] или полный `black_tea_lemon` без `serve`, **THEN** false для любого шага.
36. **[Logic]** **GIVEN** S, которая не является префиксом ни одного рецепта (например, [`cup`, `leaf_black`, `water_80`]), **WHEN** проверяется любой шаг, **THEN** false.
