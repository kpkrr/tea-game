## Summary

Механика сборки напитка: бариста держит одну чашку, добавляет шаги рецепта
на мгновенных станциях, ставит чашку в один из двух чайников на фоновую
заварку (`t_brew` = 3.0 с) и паркует чашки в 7 слотах обменом одним тапом.
Неверная вода портит чашку, её выбрасывают тапом по станции чашек. Эта
система превращает рецепты и перемещение в само действие «собрать и
заварить», на котором держится суета партии.

> **Quick reference** — Layer: `Feature` · Priority: `MVP` · Key deps: `Order & Recipe System, Player Control / Barista Movement, Kitchen & Station Layout`

## Overview

Brewing & Crafting Mechanic — механика сборки напитка: бариста держит в
руках одну чашку и тапает станции по шагам рецепта (лист → вода нужной
температуры → лимон), а заварка на чайнике идёт таймером в фоне — не
блокирует бариста для других дел, но занимает сам чайник, пока готовый чай
не заберут. Слоты у острова и стен позволяют держать несколько чашек в
разной стадии одновременно: тап по слоту одним действием меняет чашку в
руках на чашку в слоте. Неверный шаг (не та температура воды, не тот
порядок) портит чашку — она уходит в мусорку, рецепт начинается заново.
Без этой системы «Хаос за стойкой» не работает: рецепты Order & Recipe
остаются просто данными, а перемещение Player Control — просто ходьбой;
здесь они становятся реальным действием «взять — заварить — подать», из
которого складывается суета партии.

## Detailed Design

### Core Rules

**Модель данных.** Чашка — `{steps: Array[StringName], ruined: bool}`. Бариста
держит **не более одной** чашки одновременно (`held_cup: Cup | null`).
Совпадение чашки с рецептом (`matches(steps)`) и грамматика следующего шага
(`is_valid_next(steps, x)`) — контракты Order & Recipe System (эта система
их не переопределяет, только вызывает).

1. **Одна чашка в руках.** `held_cup` — либо `null` (руки пусты), либо ровно
   одна чашка. Вторую чашку получить нельзя, пока руки не освобождены (тапом
   по слоту или чайнику, см. ниже).
2. **Мгновенные станции** (`cup`, `leaf_black`, `leaf_green`, `iced_tea`,
   `lemon`) выполняют действие за один тик Holding — без таймера. Таблица
   ответа Player Control (Rule 8 — «выполнить / ждать / отказать»):

   | Станция | Состояние рук | Ответ |
   |---|---|---|
   | `cup` | `null` (пусто) | **выполнить**: новая пустая чашка `{steps: [cup]}` |
   | `cup` | чашка с `ruined = true` | **выполнить**: испорченная чашка уничтожается, выдаётся новая пустая (замена мусорки — см. Edge Cases) |
   | `cup` | любая другая чашка | **отказать** (руки заняты, вторую чашку взять нельзя) |
   | `leaf_black` / `leaf_green` / `iced_tea` / `lemon` | `null` | **отказать** (нечего наполнять) |
   | `leaf_black` / `leaf_green` / `iced_tea` / `lemon` | чашка, `is_valid_next(steps, шаг) == true` | **выполнить**: шаг добавляется в `steps` |
   | `leaf_black` / `leaf_green` / `iced_tea` / `lemon` | чашка, `is_valid_next == false` (включая `ruined`) | **отказать**, станция мигает красным |

   «Мгновенно» означает без собственного таймера этой системы — сам приход
   бариста и один тик Holding занимает Player Control, эта система решает
   в тот же тик.

3. **Чайники — асинхронные станции** (`water_100`, `water_80`). MVP: по
   одному экземпляру каждого типа (сингл-инстанс на кухню — как в
   прототипе; см. Open Questions, если Kitchen & Station Layout когда-нибудь
   введёт вторые экземпляры). У чайника три состояния: `EMPTY`,
   `BREWING(cup, t_remaining)`, `READY(cup)` (States and Transitions ниже).
   Классификация чашки в руках относительно чайника температуры `T`:
   - **MATCH** — `is_valid_next(steps, water_T) == true` (лист уже добавлен,
     температура верная).
   - **WRONG_TEMP** — последний шаг чашки — лист **другой** температуры
     (`leaf_black` у `water_80`, `leaf_green` у `water_100`). Order & Recipe
     явно оставляет решение «отказать или испортить» этой системе (Core
     Rule 3, Edge Cases) — решение: **испортить**, как в валидированном
     плейтестом прототипе (`kitchen-core` README: «не та вода — чашка не
     совпадёт ни с одним заказом, только в мусорку»).
   - **EMPTY_HANDS** — руки пусты.
   - **OTHER** — любая другая чашка (без листа, уже с водой, готовая,
     испорченная).

   Таблица ответа (все 12 комбинаций состояние×классификация):

   | Состояние чайника | Классификация | Ответ | Эффект |
   |---|---|---|---|
   | `EMPTY` | MATCH | **выполнить** | чашка уходит из рук в чайник → `BREWING(cup, t_brew)`; руки пусты |
   | `EMPTY` | WRONG_TEMP | **выполнить** (порча) | чашка в руке помечается `ruined = true`; чайник остаётся `EMPTY` (полив впустую, но без потери времени чайника) |
   | `EMPTY` | EMPTY_HANDS | **отказать** | — |
   | `EMPTY` | OTHER | **отказать** | — |
   | `BREWING` | MATCH | **ждать** | бариста стоит; предложение повторяется каждый тик (Player Control Rule 8), пока не готово |
   | `BREWING` | EMPTY_HANDS | **ждать** | то же — бариста готов забрать, как только будет готово |
   | `BREWING` | WRONG_TEMP | **отказать** | полить нельзя (чайник занят), ждать бессмысленно — см. правило ниже |
   | `BREWING` | OTHER | **отказать** | то же |
   | `READY` | MATCH | **выполнить** | обмен одним тапом: готовая чашка → руки; чашка из рук → чайник, `BREWING(cup, t_brew)` |
   | `READY` | EMPTY_HANDS | **выполнить** | готовая чашка → руки; чайник → `EMPTY` |
   | `READY` | WRONG_TEMP | **отказать** | руки заняты неподходящей чашкой |
   | `READY` | OTHER | **отказать** | то же |

   **Правило «ждать» только там, где исход гарантирован.** «Ждать»
   возвращается только для MATCH и EMPTY_HANDS при `BREWING` — единственных
   классификаций, для которых наступление `READY` гарантированно даёт
   **выполнить**. Для WRONG_TEMP/OTHER при `BREWING` — сразу **отказать**:
   ожидание никогда не привело бы к действию (Player Control: «бариста
   никогда не застревает у недопустимой цели»).

4. **Слоты — безусловный обмен.** 7 слотов (Kitchen & Station Layout: 5
   остров + 2 у стен) не проверяют содержимое. Тап по слоту **всегда
   выполняется**: чашка в руках (или `null`) меняется местами с чашкой в
   слоте (или `null`). Испорченная чашка (`ruined = true`) может быть
   поставлена в слот как обычная — освобождение слота от неё требует
   отдельного визита к станции `cup` (Rule 2) после того, как её забрали
   оттуда тем же обменом.
5. **Подача — не входит в эту систему.** Право подать чашку гостю
   (`matches(held_cup.steps)`) решают Guest AI & Patience / Order & Recipe
   System (контракт уже зафиксирован в `player-control-barista-movement.md`
   → Interactions). Эта система лишь предоставляет читаемое состояние
   `held_cup` и выполняет `consume_held_cup()` — очистку рук до `null` —
   когда вызывающая система подтверждает успешную подачу.
6. **Фоновый таймер.** `t_remaining` чайника в состоянии `BREWING`
   уменьшается каждый кадр симуляции независимо от местоположения и
   действий бариста. По достижении 0 чайник переходит `BREWING` → `READY`
   без участия игрока — этим и объясняется «таймер идёт в фоне, не
   блокирует бариста» (Overview, systems-index).

### States and Transitions

**Чашка** (владеет эта система; жизненный цикл начинается и заканчивается
вне неё — станция `cup` создаёт, `consume_held_cup()`/порча уничтожают):

| Состояние | Вход | Выход |
|---|---|---|
| Не существует | — | Тап `cup` с пустыми руками → создана `{steps: [cup]}` |
| В процессе сборки (`ruined = false`) | Создана; или шаг добавлен, но `matches() == none` | Шаг добавлен (Rule 2/3) → остаётся «в процессе» или становится «готова к подаче»; неверная вода (Rule 3, WRONG_TEMP) → «испорчена» |
| Готова к подаче | Добавленный шаг делает `matches(steps) != none` (проверяет Order & Recipe) | Подана гостю (`consume_held_cup()`, владеет Guest AI) → уничтожена; или дальнейший шаг (лимон) переводит в другой рецепт того же семейства (см. `order-recipe-system.md` Edge Cases — префикс) |
| Испорчена (`ruined = true`) | WRONG_TEMP на чайнике (Rule 3) | Тап `cup` (Rule 2) → уничтожена, выдана новая пустая |

**Чайник** (`water_100`, `water_80` — два независимых экземпляра, own state
каждый):

| Состояние | Entry | Exit |
|---|---|---|
| `EMPTY` | Старт партии; `READY` → чашку забрали без замены (Rule 3, READY+EMPTY_HANDS) | MATCH-чашка вставлена (Rule 3, EMPTY+MATCH) → `BREWING` |
| `BREWING(cup, t)` | Чашка вставлена в `EMPTY` или `READY` (обмен) | `t` достигает 0 (Rule 6, фоновый тик) → `READY(cup)` |
| `READY(cup)` | Таймер `BREWING` истёк | Чашку забрали (Rule 3, READY+EMPTY_HANDS или READY+MATCH-обмен) → `EMPTY` или `BREWING` (если сразу поставили новую) |

**Слот** — `EMPTY` / `HOLDING(cup)`, переход в любую сторону — безусловный
обмен по Rule 4.

| Audio & Juice Feedback ⚠️ *(не спроектирована, Vertical Slice)* | Downstream (soft) | События: шаг добавлен, чашка испорчена, чайник готов — на что реагировать звуком |

## Formulas

*Составлено с `systems-designer`. Значение `t_brew_base` = 3.0 с
подтверждено, не изменено: оно уже было игровым (не заглушкой) значением
`TUNING.brew_time` в плейтест-провалидированном прототипе `kitchen-core`
(плейтест 2026-09-27) и уже используется как временная метка в
`order-recipe-system.md` Formula 2. Меняется только форма — голая
константа становится формулой с множителем прокачки, потому что
`order-recipe-system.md` (Edge Cases) уже фиксирует факт «прокачка
ускоряет и ходьбу, и заварку» (Progression & Upgrades, Alpha), и без этой
формулы GDD пришлось бы переоткрывать не ради числа, а ради формы.*

### Formula 1 — `t_brew` (длительность заварки чайника)

Заварка запускается только переходом чайника `EMPTY → BREWING` при
классификации MATCH (Core Rule 3); длительность определяет момент, когда
`BREWING` сам переходит в `READY` (Core Rule 6 — фоновый таймер,
не зависящий от местоположения бариста).

The `t_brew` formula is defined as:

`t_brew = t_brew_base / speed_multiplier`

**Variables:**

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `t_brew_base` | float, с | 3.0 (фиксировано) | constant (эта GDD; playtest-validated — `prototypes/kitchen-core` `TUNING.brew_time`, плейтест 2026-09-27) | Длительность заварки при `speed_multiplier` = 1.0 (базовый темп MVP, без прокачки) |
| `speed_multiplier` | float | {1.0, 1.15, 1.3, 1.5} | Progression & Upgrades (Alpha); тот же множитель, что в `effective_speed` (`player-control-barista-movement.md`, Formula 1); в MVP всегда 1.0 | Множитель прокачки темпа — одна прокачка ускоряет и ходьбу, и заварку (см. `order-recipe-system.md`, Edge Cases) |
| `t_brew` | float, с | 2.0–3.0 | calculated | Секунды до перехода конкретного экземпляра чайника `BREWING` → `READY`; отсчитывается независимо для каждого из двух чайников (`water_100`, `water_80`) |

**Output Range:** [2.0, 3.0] с — верхняя граница `t_brew_base / 1.0` = 3.0 с
(MVP, единственное достижимое значение до Alpha), нижняя
`t_brew_base / 1.5` ≈ 2.0 с (максимальный уровень прокачки, Alpha).
`speed_multiplier` берётся из фиксированного зарегистрированного множества
— `t_brew` не выходит за эти границы ни при каких данных. Таймер общий не
между чайниками: `water_100` и `water_80` отсчитывают независимо.
**Example:** MVP (`speed_multiplier` = 1.0) — бариста в момент `t = 10.0` с
партии кладёт в пустой `water_100` чашку `[cup, leaf_black]` (MATCH) →
`t_brew = 3.0 / 1.0 = 3.0` с → чайник сам переходит `BREWING` → `READY` в
`t = 13.0` с, даже если бариста в это время уже обслуживает другого гостя.
Alpha-пример (средний уровень прокачки, `speed_multiplier` = 1.3):
`t_brew = 3.0 / 1.3 ≈ 2.31` с.

**Проверка на «узкое место».** MVP отгружает ровно 2 чайника (по одному на
температуру). При пиковом потоке гостей 18/мин (≈0.3 гостя/с),
поделённом поровну между чёрным и зелёным семейством, на каждый чайник
приходится ≈0.15 запроса/с; utilization ≈ 0.15 × 3.0 ≈ **0.45** —
заметно ниже насыщения (1.0) даже на пике сложности партии. Значит,
`t_brew_base` = 3.0 с не создаёт искусственный потолок пропускной
способности — предел по-прежнему держится на мастерстве маршрутов
бариста (Player Control), а не на аппаратной занятости чайника. Соотношение
с `t_step` = 2.0 с (среднее время шага «дойти+тапнуть», авторитетно в
`player-control-barista-movement.md`) тоже осмысленно: `t_brew_base` ≈
1.5 × `t_step` — бариста успевает сделать один реальный шаг в другом месте,
пока чай доваривается, но не гарантированно с большим запасом; будь
`t_brew` меньше `t_step`, решение «уйти или подождать» стало бы
тривиальным (уходить почти никогда не успевать), будь оно намного больше
(8–10 с) — тривиальным в обратную сторону и подняло бы utilization выше
безопасной зоны.

### Влияние на `order-recipe-system.md`

Пересчитывать `coins_per_sec` не нужно: `t_brew_base` = 3.0 с в точности
совпадает со значением, которое Formula 2 того GDD уже использует как
временную метку — она становится авторитетной без изменения числа. При
следующем касании `order-recipe-system.md` снять пометку «прототип,

GDD; таблица `coins_per_sec` (0.333–0.700) и вывод Open Question остаются
в силе без изменений.

## Edge Cases

*Систем-дизайнер не привлекался для этой секции — режим `lean` (агент
зарезервирован для Formulas и Acceptance Criteria). Разбор построен на
таблицах Core Rules и явных открытых вопросах, которые Order & Recipe
System и Player Control передали этой GDD.*

**Заварка и чашка в руках**

- **Если лимон нужно добавить до окончания таймера заварки** (открытый
  вопрос `order-recipe-system.md`): **невозможно структурно**, не
  политикой. Пока чашка в состоянии `BREWING`, она физически лежит в
  чайнике, а не в руках бариста (Core Rule 3/4) — добавить шаг может
  только чашка в руках (Core Rule 2). Лимон становится доступен только
  после того, как чашка забрана из `READY` в руки.
- **Если чашка уже совпадает с более простым рецептом того же семейства**
  (например, готовый `black_tea` после забора из чайника) и бариста
  добавляет лимон: разрешено — `is_valid_next(steps, lemon)` истинно после
  шага воды (грамматика Order & Recipe), чашка становится
  `black_tea_lemon`. Подтверждение правила «префикс — legal intermediate
  state», которым владеет Order & Recipe, не новое правило этой системы.
- **Если в чашке ещё нет листа, а бариста тапает чайник** (`cup` → сразу
  `water_100`/`water_80`, минуя лист): классифицируется как **OTHER**, не
  **WRONG_TEMP** — порчи нет, просто отказ (станция мигает красным).
  Порча происходит только когда последний шаг чашки — лист **другого**
  цвета, чем чайник (Core Rule 3).
- **Если к чайнику подносят уже испорченную чашку** (`ruined = true`):
  классифицируется как **OTHER** независимо от того, какой лист был до
  порчи — повторная порча или заварка невозможны, чайник просто отказывает
  в любом своём состоянии.
- **Если бариста добавляет воду дважды** (чашка уже содержит `water_100`
  или `water_80`, тап по любому чайнику): `is_valid_next` ложно (грамматика
  не допускает повторный шаг того же типа) → **OTHER** → отказ, порчи нет
  (это не temperature-mismatch, а избыточный шаг).

**Прерывания и параллельность**

- **Если новый тап уводит бариста от чайника, где он «ждёт» (`BREWING` +
  MATCH/EMPTY_HANDS)**: ожидание прерывается немедленно (Player Control
  Rule 3 — последний тап побеждает всегда), но таймер чайника **продолжает
  идти в фоне** (Core Rule 6) — не привязан к присутствию бариста. Можно
  вернуться позже, чайник будет `READY`, если время истекло.
- **Если гость ушёл (терпение кончилось), пока бариста нёс к нему
  совпадающую чашку**: подача не состоялась, `consume_held_cup()` не
  вызывается — чашка остаётся в руках без изменений; её можно подать
  другому гостю с тем же заказом или временно поставить в слот. Эта
  система ничего не теряет и не восстанавливает откат.
- **Если оба чайника заняты и все 7 слотов заполнены, а бариста хочет новую
  чашку**: `cup`-станция проверяет только состояние **рук**, не слотов
  (Core Rule 2) — если руки пусты, новая чашка выдаётся всегда. Игровой
  затор (все станции заняты сборкой) — валидное, ожидаемое состояние
  хаотичной партии (Pillar 1), не ошибка данных и не deadlock: у бариста
  всегда остаётся минимум одно свободное «рабочее место» — собственные
  руки.

**Прокачка (Alpha) и пауза**

- **Если бариста прокачан скоростью** (`speed_multiplier` > 1.0,
  Progression & Upgrades, Alpha): длительность заварки уже определена как
  `t_brew = t_brew_base / speed_multiplier` (Formulas, Formula 1) — тот же
  множитель, что и на `effective_speed` ходьбы (`player-control-barista-movement.md`
  Formula 1), потому что прокачка описана как «быстрее готовка и
  передвижение» (game-concept, Core Loop). В MVP `speed_multiplier` всегда
  1.0, `t_brew` = `t_brew_base` = 3.0 с. Цены рецептов не пересчитываются —
  решение уже зафиксировано как прецедент в `order-recipe-system.md` Edge
  Cases.
- **Если приложение уходит в фон** (Platform Integration, сигнал паузы —
  soft-зависимость Player Control): все таймеры `BREWING` останавливаются
  вместе с общей паузой партии и возобновляются с того же `t_remaining`
  при возврате — иначе сворачивание приложения превращалось бы в способ
  «превысить» реальное время заварки без усилия игрока.

**Сброс состояния**

- **Начало новой партии**: все чайники → `EMPTY`, все 7 слотов → `EMPTY`,
  `held_cup` бариста → `null`. Состояние предыдущей партии не переносится
  (партии независимы — как и вся остальная экономика вне кассы).

**Целостность данных**

- **Если Kitchen & Station Layout когда-либо введёт больше одного
  экземпляра `water_100` или `water_80`** (MVP предполагает ровно один на
  тип — см. Open Questions): каждый экземпляр ведёт свой независимый
  `EMPTY`/`BREWING`/`READY`, эта GDD не требует правок — модель уже
  per-instance.

### Чайник: 3 состояния с одного взгляда

Два чайника — пропускная способность средних и сложных заказов. Игрок
читает их состояние периферийным зрением, на бегу решая «ждать или уйти»,
поэтому кодирование — движением и контрастом, не мелкими иконками.

| Состояние | Корпус | Пар | Акцент |
|---|---|---|---|
| `EMPTY` | Оттенок своего типа (`water_100` красный, `water_80` синий), приглушённая светлота и насыщенность | Нет | Нет, статично (пустые станции без idle-анимации — правило Kitchen & Station Layout) |
| `BREWING` | Полная насыщенность своего оттенка | Непрерывная анимация, 3 стадии по трети `t_brew`: тонкая струйка → средний плюм → полный джет | Нет |
| `READY` | Тот же оттенок | Оседает в один тонкий завиток — смена характера движения | Тёплый ободок-блик (та же метафора, что «Совпадает с заказом» у чашки) + лёгкое покачивание крышки |

Прогресс — диегетический (стадии пара), без радиальной шкалы: готовый чай
не портится, поэтому точные секунды игроку не нужны, нужно «рано / скоро /
готово».

### Слот

| Состояние | Визуал |
|---|---|
| `EMPTY` | Нейтральный оттиск-кольцо в тон столешницы; ни один из 7 цветов шагов не используется — слот не привязан к типу станции |
| `HOLDING(cup)` | Спрайт чашки с теми же 3 состояниями, с мягкой тенью — «стоит на столе» |

Обмен в слоте безусловный (Core Rule 4) и без отклика казался бы «ничего не
произошло»: при постановке и снятии — короткое приземление чашки
(сплющивание-отскок, 2–3 кадра), анимацией самого спрайта, без отдельного
VFX.

### Звуковые события-кандидаты

Спецификация — Audio & Juice Feedback (Vertical Slice). Звук никогда не
единственный носитель информации: у каждого события есть визуальный дубль.

| Событие | Приоритет | Интонация | Визуальный дубль |
|---|---|---|---|
| Чайник → `READY` | Высокий, не тревожный (ожидание не штрафуется) | Короткий тёплый восходящий сигнал | Осевший пар + тёплый ободок |
| Чашка испорчена | Высокий (обучающий момент) | Короткий глухой тон, отличим от положительных, но не «буззер провала» | Мутная жидкость без пара, крестик, обесцвеченные жетоны |
| Шаг добавлен | Средний, самый частый — короткий, неутомляющий | Лёгкий сухой щелчок, тембр может зависеть от станции | Жетон становится полноцветным |
| Чашка вставлена в чайник | Низкий | Мягкое короткое наливание | Пар появляется |

### Проверка конфликтов с палитрой

- Оттенок корпуса чайника не меняется между состояниями — он остаётся
  тождеством типа воды (как жетон рецепта); состояния — светлотой,
  насыщенностью, паром и ободком. «Красный = ошибка» не появляется.
- Тёплый ободок `READY` — повтор уже одобренного «тёплый блик = забери», не
  новый цвет.
- Порча — глухой сигнал без красного и без зуммера.

## Game Feel

### Feel Reference

Не таймбар и не мини-игра на реакцию — «поставил чай и забыл» из
short-order-cook жанров (референс — фоновая заварка в Cooking Fever, где
можно уйти и вернуться). Анти-референс: любой QTE или точный тайминг-бар
на сборе готового чая — это противоречило бы прототипу, который явно
зафиксировал «готовая заварка ждёт сколько угодно» (kitchen-core README):
момент сбора никогда не наказывает за опоздание, только за то, что чайник
дольше простаивает без дела для следующей чашки.

- **Старт заварки — маленькое обязательство, не действие с наградой.** Тап
  по чайнику с верным листом не должен ощущаться как «выполнено» так же
  сочно, как подача гостю (это чужая, более крупная награда) — короткая,
  тихая реакция (см. Visual/Audio), после которой внимание игрока сразу
  уходит дальше. Держать взгляд на чайнике незачем — фоновый таймер и есть
  весь смысл механики.
- **Порча — мгновенная и честная, не наказывающая.** В момент неверной
  воды чашка портится без анимации ожидания или второго шанса: игрок сразу
  видит результат своей ошибки и может немедленно начать заново у станции
  `cup` (Edge Cases). Задержка здесь работала бы против Pillar 1 (суета
  важнее глубины) — цена ошибки уже есть в потраченном времени похода к
  чайнику, добавлять штраф-паузу не нужно.
- **Обмен на чайнике одним тапом — самый «сочный» момент механики.**
  Забрать готовое и сразу поставить новое одним действием (Core Rule 3,
  READY+MATCH) — это момент, где опытный игрок обгоняет партию; он должен
  ощущаться быстрее и увереннее, чем любой другой тап станции, а не
  идентично простому сбору.
- **Ожидание у чайника («ждать», Rule 3) не должно ощущаться как
  зависание.** Поза Holding принадлежит Player Control (его
  Visual/Audio); здесь объяснение ожидания даёт сам чайник — активный пар
  `BREWING` рядом с бариста читается как «жду осознанно», а не как «баг,
  персонаж завис».

### Weight and Responsiveness

Скорость самого действия (не хождения) везде одинакова и не тюнингуется
этой GDD: мгновенные станции выполняют действие за 1 тик Holding (Core
Rule 2) — разницы в отклике между «добавить лист» и «добавить лимон» нет,
и не должно быть, иначе сложные рецепты начнут ощущаться механически
тяжелее лёгких, а не только дороже по времени. Единственная переменная
длительность во всей системе — сам `t_brew` (Formulas), и она сознательно
не управляется вводом игрока (нельзя «ускорить» тапаньем) — это защищает
Pillar 1 test «шаг, который не добавляет суеты, вырезается»: тайминг-мини-
игра на заварке добавила бы глубину, а не суету.

### Feel Acceptance Criteria

- **GIVEN** бариста тапает чайник с верной парой лист+вода, **WHEN** тап
  зарегистрирован, **THEN** визуальная и звуковая реакция происходит в тот
  же кадр, без задержки на анимацию «начала заварки».
- **GIVEN** чайник в состоянии `READY`, **WHEN** бариста подходит с новой
  валидной чашкой, **THEN** обмен (забрать+поставить) читается как единое
  быстрое действие, а не как два последовательных.

## UI Requirements

Своих экранов и виджетов у системы нет — весь фидбек живёт в мире (чашка,
чайники, слоты), не в HUD. Требования к HUD & Feedback UI, вытекающие из
этой системы:

1. Состояние чайников и слотов не дублируется экранным виджетом в полосах
   HUD — оно видно в мире (кухня всегда целиком на экране, Kitchen &
   Station Layout Game Feel). Если индикатор над чайником рисует система
   HUD, он привязан к мировой позиции чайника, как заполнение кассы к till
   anchor.
2. HUD обязан отражать содержимое `held_cup` в тикете текущего заказа —
   если у гостя, к которому идёт бариста, заказ совпадает с чашкой в руках,
   это должно быть видно без взгляда на саму чашку (уже частично покрыто
   `order-recipe-system.md`: цветные жетоны рецепта на тикете).
3. Ни один из статусов чашки (Собирается/Совпадает/Испорчена — владеет
   Order & Recipe) не дублируется отдельной иконкой в HUD — источник
   истины один, сама чашка в мире.

## Acceptance Criteria

*Составлено с `qa-lead`. Каждый критерий проверяется тестировщиком без
чтения GDD. Критерии ощущения — в Game Feel → Feel Acceptance Criteria.
Фикстуры: фабрика `BrewingFixtures` — чашка, два независимых чайника
(`water_100`, `water_80`), 7 слотов; внешний шаг симуляции `step(delta)`
для фонового таймера (Core Rule 6), тем же паттерном, что
`BaristaFixtures` в `player-control-barista-movement.md`. Грамматика и
совпадение (`is_valid_next`, `matches`) подставляются заглушкой
`FakeRecipeGrammar` (сценарные ответы) — зависимость от Order & Recipe
System изолируется для юнит-тестов (Testing Standards → Independence).
Logic → `tests/unit/brewing_crafting/`, файлы
`brewing_crafting_[feature]_test.gd`. Integration →
`tests/integration/brewing_crafting/`, сцены `kitchen_fixture_*` (реальные
Order & Recipe System и Player Control вместо заглушек). Форма API
(сигналы, методы) — в ADR.*

Обозначения: **«подходящая чашка»** — чашка с листом, для которого этот
чайник — следующий верный шаг рецепта. **«Чашка не того листа»** — чашка,
последний ингредиент которой — лист, требующий воды ДРУГОЙ температуры.

### Core Rule 1 — одна чашка в руках

- **[Logic] AC-1.1 GIVEN** у бариста пустые руки, **WHEN** игрок тапает станцию
  выдачи чашек, **THEN** в руках появляется ровно одна новая пустая чашка.
- **[Logic] AC-1.2 GIVEN** в руках бариста любая неиспорченная чашка, **WHEN**
  игрок тапает станцию выдачи чашек, **THEN** действие отклоняется: вторая
  чашка не создаётся, чашка в руках не заменяется.
- **[Logic] AC-1.3 GIVEN** идёт партия, **WHEN** состояние бариста проверяется в
  любой момент, **THEN** он держит ноль или одну чашку — никогда больше.

### Core Rule 2 — мгновенные станции

- **[Logic] AC-2.1 GIVEN** в руках испорченная чашка, **WHEN** игрок тапает станцию
  выдачи чашек, **THEN** испорченная чашка исчезает, в руках — новая пустая.
- **[Logic] AC-2.2 GIVEN** пустые руки, **WHEN** игрок тапает станцию листа, льда
  или лимона, **THEN** действие отклоняется, чашка не создаётся.
- **[Logic] AC-2.3 GIVEN** в руках чашка, для которой ингредиент станции —
  допустимый следующий шаг, **WHEN** игрок тапает станцию, **THEN**
  ингредиент добавляется в тот же тик, без таймера.
- **[Logic] AC-2.4 GIVEN** в руках чашка, для которой ингредиент станции — НЕ
  допустимый следующий шаг, **WHEN** игрок тапает станцию, **THEN** чашка
  не меняется, станция даёт визуальный сигнал отказа.

### Core Rule 3 — чайники

- **[Logic] AC-3.1 GIVEN** чайник пуст, в руках «подходящая чашка», **WHEN** тап
  по чайнику, **THEN** чашка уходит в чайник, начинается заварка, руки пусты.
- **[Logic] AC-3.2 GIVEN** чайник пуст, в руках «чашка не того листа», **WHEN** тап
  по чайнику, **THEN** чашка остаётся в руках и помечается испорченной,
  чайник остаётся пустым.
- **[Logic] AC-3.3 GIVEN** чайник пуст, руки пусты, **WHEN** тап по чайнику,
  **THEN** отказ, состояние чайника не меняется.
- **[Logic] AC-3.4 GIVEN** чайник пуст, в руках чашка без листа или уже
  испорченная, **WHEN** тап по чайнику, **THEN** отказ, чашка не меняется
  и не портится.
- **[Logic] AC-3.5 GIVEN** чайник заваривает, в руках «подходящая чашка», бариста
  стоит у чайника, **WHEN** заварка завершается, **THEN** без повторного
  тапа готовая чашка оказывается в руках, а принесённая — в чайнике с
  новым отсчётом.
- **[Logic] AC-3.6 GIVEN** чайник заваривает, руки пусты, бариста стоит у чайника,
  **WHEN** заварка завершается, **THEN** без повторного тапа готовая чашка
  оказывается в руках, чайник пуст.
- **[Logic] AC-3.7 GIVEN** чайник заваривает, в руках «чашка не того листа»,
  **WHEN** тап по чайнику, **THEN** немедленный отказ (бариста не остаётся
  ждать), чашка не портится, заварка продолжается.
- **[Logic] AC-3.8 GIVEN** чайник заваривает, в руках чашка без листа, **WHEN** тап
  по чайнику, **THEN** немедленный отказ, ничего не меняется.
- **[Logic] AC-3.9 GIVEN** чайник готов, в руках «подходящая чашка», **WHEN** один
  тап по чайнику, **THEN** за одно нажатие готовая чашка в руках, принесённая
  — в чайнике с запущенной заваркой.
- **[Logic] AC-3.10 GIVEN** чайник готов, руки пусты, **WHEN** тап по чайнику,
  **THEN** готовая чашка в руках, чайник пуст.
- **[Logic] AC-3.11 GIVEN** чайник готов, в руках «чашка не того листа», **WHEN**
  тап по чайнику, **THEN** отказ; готовая чашка остаётся в чайнике, чашка
  в руках не портится.
- **[Logic] AC-3.12 GIVEN** чайник готов, в руках чашка без листа, **WHEN** тап по
  чайнику, **THEN** отказ, готовая чашка остаётся в чайнике.

### Core Rule 4 — слоты

- **[Logic] AC-4.1 GIVEN** в слоте чашка, в руках другая чашка (любые, включая
  испорченные), **WHEN** тап по слоту, **THEN** чашки меняются местами;
  отказа не бывает.
- **[Logic] AC-4.2 GIVEN** слот пуст, в руках чашка, **WHEN** тап по слоту,
  **THEN** чашка в слоте, руки пусты.
- **[Logic] AC-4.3 GIVEN** в слоте чашка, руки пусты, **WHEN** тап по слоту,
  **THEN** чашка в руках, слот пуст.

### Core Rule 5 — подача (только очистка рук)

- **[Logic] AC-5.1 GIVEN** в руках чашка, **WHEN** внешняя система вызывает
  `consume_held_cup()`, **THEN** руки мгновенно пусты.
- **[Logic] AC-5.2 GIVEN** в руках чашка, **WHEN** `consume_held_cup()` не
  вызывается, **THEN** чашка не исчезает и не меняется сама по себе.

### Core Rule 6 — фоновый таймер

- **[Logic] AC-6.1 GIVEN** чайник заваривает, **WHEN** бариста уходит и делает
  другие действия, **THEN** отсчёт идёт без остановки.
- **[Logic] AC-6.2 GIVEN** чайник заваривает, **WHEN** отсчёт достигает нуля,
  **THEN** чайник становится готовым без действий игрока.
- **[Logic] AC-6.3 GIVEN** оба чайника заваривают с разным остатком времени,
  **WHEN** время идёт, **THEN** каждый становится готовым в свой момент,
  независимо от другого.

### Formula 1 — `t_brew`

- **[Logic] AC-F1.1 GIVEN** MVP-сборка (без прокачки), **WHEN** чашка помещена в
  любой чайник, **THEN** она готова через 3.0 с (± 1 кадр).
- **[Logic] AC-F1.2 GIVEN** заварка начата при t = 10.0 с партии, **WHEN** идёт
  время, **THEN** чайник готов при t = 13.0 с (± 1 кадр).
- **[Logic] AC-F1.3 GIVEN** `speed_multiplier` из набора {1.0, 1.15, 1.3, 1.5}
  (Alpha, unit-тест формулы), **WHEN** вычисляется `t_brew`, **THEN**
  результат равен `3.0 / speed_multiplier` и лежит в [2.0, 3.0] с.

### Edge Cases

- **[Logic] AC-E1 GIVEN** испорченная чашка в руках, **WHEN** игрок пробует любой
  чайник или станцию листа/льда/лимона, **THEN** все отклоняются;
  единственный выход — станция выдачи чашек (AC-2.1) или слот (AC-4.1).
- **[Logic] AC-E2 GIVEN** чашка заваривается в чайнике, руки пусты, **WHEN** тап по
  станции лимона, **THEN** отказ как «пустые руки» — лимон не попадает в
  чашку внутри чайника.
- **[Logic] AC-E3 GIVEN** бариста ждёт у заваривающего чайника, **WHEN** новый тап
  уводит его к другой цели, **THEN** отсчёт в чайнике не меняется.
- **[Logic] AC-E4 GIVEN** конец партии в любом состоянии, **WHEN** начинается
  новая партия, **THEN** оба чайника пусты, все 7 слотов пусты, руки пусты.
- **[Logic] AC-E5 GIVEN** чайник заваривает с остатком 1.2 с, **WHEN** приложение
  уходит в фон и возвращается, **THEN** отсчёт возобновляется с 1.2 с, а не
  завершается за время в фоне.
- **[Logic] AC-E6 GIVEN** оба чайника заняты, все 7 слотов заполнены, руки пусты,
  **WHEN** тап по станции выдачи чашек, **THEN** новая чашка выдаётся.
- **[Logic] AC-E7 GIVEN** в руках готовая чашка, гость-адресат ушёл, **WHEN**
  `consume_held_cup()` не вызывается, **THEN** чашка остаётся в руках.
